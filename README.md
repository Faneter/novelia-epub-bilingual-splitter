# novelia-epub-bilingual-splitter

把「日文原文 + 中文译文」逐段交织排版的 EPUB，拆成两本各自单语的 EPUB。

日文版只留原文并去掉淡化样式，中文版只留译文（自动不含日文注音），插图、目录、版权页两本都完整保留。

```console
$ cargo run -- "zh-jp.Ys.幼女系底辺ダンジョン配信者、…_1.epub"
源 EPUB: zh-jp.Ys.幼女系底辺ダンジョン配信者、…_1.epub
读入 35 个条目
书名: 日文版「幼女系底辺ダンジョン配信者、…」 / 中文版「幼女系底辺ダンジョン配信者、…」

=== [ja] zh-jp.Ys.幼女系底辺ダンジョン配信者、…_1.ja.epub ===
  保留 日文段  4765 / 中文段     0 / 中立段  378 / 丢弃  4765
  产物 35 个条目，首条目 mimetype(Stored) ✓ 符合规范
  正文 4765 段（另有图片/空行 378 段）；残留淡化样式 0 段；疑似混入另一种语言 0 段

=== [zh] zh-jp.Ys.幼女系底辺ダンジョン配信者、…_1.zh.epub ===
  保留 日文段     0 / 中文段  4765 / 中立段  378 / 丢弃  4765
  产物 35 个条目，首条目 mimetype(Stored) ✓ 符合规范
  正文 4765 段（另有图片/空行 378 段）；残留淡化样式 0 段；疑似混入另一种语言 3 段
  ⚠ 3 段正文含日文假名，可能是译本里保留的专有名词，也可能是漏翻
      · 《红豆：真央，冷静下来听我说……你竟然在ダンTV的在线人数排行榜上排名第一了！》
      · 我慌忙看了看ダンTV的主页，有几十万的拾荒者们正在日本各地直播。
      · 负责插画的とくまろ老师。看到角色设计的时候，我还在想“你是神吗？”但看到封面和插画后，我确信您是神。您一定也很纯洁。

完成。
```

---

## 它解决什么问题

双语对照 EPUB 里两种语言**逐段交替**，读起来视线要来回跳：

```html
<p style="opacity:0.4;">　空から、何かが落ちてきた。</p>
<p>　有什么东西从天上掉了下来。</p>
```

想只读其中一种语言，就只能一段段手删。本项目自动完成这件事，且不依赖任何在线翻译或语言识别服务。

## 原理：不是"识别语言"，而是"读样式"

关键在于——这类源文件把两种语言**靠内联样式**区分，而不是靠内容或目录结构：

| | 源文件里的写法 | 含义 |
|---|---|---|
| 日文原文 | `<p style="opacity:0.4;">…</p>` | 淡化显示（对照排版里的"原文"） |
| 中文译文 | `<p>…</p>` | 正常显示（对照排版里的"译文"） |
| 语言无关 | `<p><br /></p>`、`<p><img …/></p>` | 空行与图片页，两本书都要保留 |

所以判别式只有一条：**段落的 `opacity` 是否小于 1**。注意判定的是"值小于 1"而不是写死 `opacity:0.4`——淡化多少因书而异。

之所以敢只靠这一条，是因为两本源书都满足：

- 段落只有"淡化 / 不淡化"两类，没有第三种变体；
- 中文段落里**假名几乎不出现**；
- 注音 `<ruby>` **只出现在日文段落里**（第一本 479 处、第二本 308 处，中文段落里 0 处）。

也就是说切分零歧义、不需要语言识别模型。顺带的好处是中文版自动不含任何日文注音。

## 快速开始

```bash
cargo run                              # 自动使用当前目录下的 .epub
cargo run -- <path.epub>               # 指定源 EPUB
cargo run -- <path.epub> --zh-title 中文书名
cargo run -- <path.epub> --ja-title 日文书名
cargo run -- <path.epub> --strict      # 把警告也当成失败
cargo test                             # 72 个测试
```

需要支持 edition 2024 的 Rust（1.85+）。开发与验证环境为 1.95.0；最低版本未逐版本验证，实际下限还可能受 `zip` 依赖约束。唯一的直接依赖是 [`zip`](https://crates.io/crates/zip)。

## 输出

| | 日文版 `*.ja.epub` | 中文版 `*.zh.epub` |
|---|---|---|
| 书名 `dc:title` | 源书 `dc:title`，缺失时从文件名推导 | 同左，可用 `--zh-title` 覆盖 |
| `dc:language` | `ja` | `zh-CN` |
| `dc:identifier` | `<源 id>-ja` | `<源 id>-zh`（源书没有时派生，保证不撞） |
| `xml:lang` | `ja` | `zh-CN` |
| `<ruby>` 注音 | 全部保留 | 无 |
| 段落 `id` / `class` | 保留 | 保留 |
| 插图 | 全部复制 | 全部复制 |
| 章标题 | 原样 | 映射表里的日文标题汉化 |

书名**一律来自源文件**（`dc:title`），源书没有时退回从文件名推导（会自动剥掉 `zh-jp.Ys.` 这类语言对/压制者前缀）。

## 两本源书的差异（都已在测试里覆盖）

工具是在两本结构差异很大的书上验证过的，这些差异正是"换一本书就不适用"的来源：

| | 第一本 `カイブツ×カノジョ` | 第二本 `幼女系底辺ダンジョン配信者` |
|---|---|---|
| 段落顺序 | 日文在前 | **中文在前** |
| 段落属性 | 只有 `style` | **还带 `id="page_*"` / `class="class_*"`（463 处）** |
| 章标题 | `<h2>` / `<h3>` | **`<h4>`，且带副标题** |
| 每文件 `<title>` | 都是书名 | **各自的章节名、甚至有论坛帖标题** |
| 容器 | EPUB 2.0 + NCX | **EPUB 3 + `nav.xhtml`** |
| `dc:identifier` | 有 | **没有，且 `unique-identifier` 悬空** |
| 根元素 `xml:lang` | `ja` | **`zh-CN`** |
| 段落总数 | 6586 | 9908 |

## 实现里必须处理的坑

1. **去掉淡化样式时要保留其它属性。** 把整个开标签换成 `<p>` 会连带丢掉 `id` / `class`——第二本源书有 463 处这样的段落，页锚点和样式类会全部消失。实现只剥掉 `opacity` 这一条声明，其余原样保留。
2. **两个方向都要改写 `xml:lang`。** 第一本源书声明 `ja`，第二本声明 `zh-CN`。只做"往中文改"这一个方向的话，第二本的日文版会声明自己是中文书。
3. **不要用书名覆盖每个文件的 `<title>`。** 第一本里每个文件的 `<title>` 恰好都是书名，改掉无所谓；第二本里那是各自的章节名（`あとがき`、`表紙`，甚至有论坛帖标题），用书名覆盖会把它们全毁掉。
4. **章标题只在整段相等时汉化。** `あとがき` → `后记`，但 `プロローグ 魔王様、うっかり爆誕してしまう` 不会被翻成半中半日。映射表覆盖 `h1`–`h6` 与 `<title>`。
5. **两本书的 `dc:identifier` 必须不同**，否则阅读器书库会当成同一本书互相覆盖。源书没有 identifier 时按书名派生一个稳定值——不能退回常量，否则任意两本无 ID 的书也会撞在一起。
6. **CSS 文件往往是 0 字节。** 样式全部内联，不能靠改 CSS 来切换语言。
7. **`mimetype` 必须是第一个条目且不压缩。** 两本源书都不符合这条规范，产物统一修正。

## 安全网：只对"真的坏了"报错

拆错一本双语书最坏的结果是"静默产出一本混着另一种语言的书"。但**过度报错同样有害**：早期版本把"中文段落里出现假名"一律当故障，结果第二本书里合法的专有名词（`ダンTV` 是虚构直播平台、`とくまろ` 是插画师）触发了误报，工具拒绝产出。

现在的判据是**证据驱动**的：

| 判据 | 处理 |
|---|---|
| `mimetype` 不合规 | ✗ 致命 |
| 产物里有残留的淡化样式（日文版会整版发灰） | ✗ 致命 |
| **某页超过 1/3 的正文段疑似判错**（判别式在该页失效） | ✗ 致命 |
| 零星段落含假名（多半是保留的专有名词） | ⚠ 提示，并列出原文供人工核对 |
| 某页在本语言下一段正文都没有 | ⚠ 提示 |

`--strict` 可把 ⚠ 也提升为失败。另外两本书各自都满足**段落守恒**：`留下的 + 丢弃的 = 源书段落总数`，不可能凭空消失或重复计入。

## 项目结构

```
src/
├── lib.rs        库根：判别式与两本源书差异的说明
├── main.rs       CLI 入口：参数、编排、打印（仅 84 行）
├── lang.rs       语言领域模型（ja / zh-CN）
├── paths.rs      决定读哪个文件、产物叫什么、书名兜底
├── epub.rs       ZIP 容器层：整包读入 / 写出
├── markup.rs     XHTML 片段层：切出 <p>、识别与剥离淡化样式
├── split.rs      核心：按样式决定段落去留
├── metadata.rs   源书元数据提取、OPF / NCX / 章标题改写
├── pipeline.rs   编排：组装出一本书
└── audit.rs      产物回读自检
tests/
└── round_trip.rs 端到端集成测试（两本真实源书 + 一本手工构造）
```

依赖方向是单向的，没有环：

```
markup ─┬─> split ────┐
        └─> metadata ─┴─> pipeline ─> main
lang ────┴──────────────────┘         ^
paths ────────────────────────────────┤
epub ─────────────────────────────────┤
audit ────────────────────────────────┘
```

两条设计约定：

- **`markup` 刻意不认识"语言"**，只认识标记结构；"淡化的是日文"这条业务规则属于 `split`。
- **所有模块返回数据、不打印**，格式化集中在 `main`。所以 `audit` 返回 `Report` 而不是直接输出，测试才能断言它。

`epub` 的读写是泛型（`Read + Seek` / `Write + Seek`），因此 `epub` 与 `audit` 的测试**全程在内存 `Cursor` 里跑**，不落任何临时文件。

## 作为库使用

各模块都是公开的，可以嵌入自己的流程：

```rust
use novelia_epub_bilingual_splitter::metadata::{Plan, SourceMeta};
use novelia_epub_bilingual_splitter::{audit, epub, lang::Lang, pipeline};

let entries = epub::read_path("book.epub".as_ref())?;

// 书名等每本书各不相同的信息由 Plan 提供；缺失时用文件名兜底。
let meta = SourceMeta::extract(&entries);
let plan = Plan::new(&meta.title, &meta.identifier);

for lang in Lang::ALL {
    let (archive, stats) = pipeline::build(&entries, lang, &plan);
    println!("[{}] 留下 {} 段，丢弃 {} 段", lang.tag(),
             stats.paragraphs.paragraphs(), stats.paragraphs.dropped);

    let mut buf = std::io::Cursor::new(Vec::new());
    epub::write(&mut buf, &archive)?;
    buf.set_position(0);

    let report = audit::inspect(buf, lang)?;
    // fatal_issues 只报「产物不合规 / 整页判错」这类真故障；
    // 零星的疑似段落走 warnings，需要人工过目。
    assert!(report.fatal_issues().is_empty());
}
```

## 已知限制

- **判别式依赖"原文被淡化"这一排版约定。** 用别的方式标记原文的书（别的 class、`display:none`、分成两个文件等）不适用。好消息是不会静默出错：约定被破坏时会触发[安全网](#安全网只对真的坏了报错)并以非零码退出。
- **章标题汉化靠一张手工映射表**，只覆盖常见的日文标签（プロローグ/エピローグ/あとがき/番外編/一〜六章）。**带副标题的标题不会被翻译**（源书里那些副标题压根没有中文对照，任何自动化都无法凭空得到译名），中文版会保留原日文标题。
- **`dc:creator` 未改写**，两本书都保留源书原文的作者名。
- **中文版沿用源书的书写方向**。若源书是竖排而你想横排，需要自行在 `metadata::rewrite_raw` 里加一处 `vrtl` → `hltr` 替换。
- **输出不是字节级可复现的**：ZIP 写入器给每个条目打上当前时间戳，所以每次运行的 SHA256 都不同。若想用哈希做产物校验，需要给写入器设一个固定时间戳。
- **未处理加密/DRM 与 EPUB 3 的 `nav.xhtml` 导航改写。** 第二本正是 EPUB 3，`nav.xhtml` 会被当作普通 XHTML 参与切分（它没有段落，因此内容不变），但导航标签本身不做汉化。
- 源书体积按整体读入内存处理（实测 2 MB / 1.5 MB）。拆几百 MB 的书需要改成流式。

## 开发环境提示

本机沙箱下 `cargo add` / 首次 `cargo build` 会失败：

```
schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS
```

这不是网络不通（DNS 正常，Node 自带的 OpenSSL 能访问 crates.io），而是沙箱令牌拿不到 Windows 加密凭据，导致 cargo 的 TLS 握手失败。**依赖已全部缓存到 `~/.cargo`，日常 `build` / `test` / `run` 不受影响**；只有新增依赖时才需要放行网络访问。
