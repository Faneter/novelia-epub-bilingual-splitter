# novelia-epub-bilingual-splitter

把「日文原文 + 中文译文」逐段交织排版的 EPUB，拆成两本各自单语的 EPUB。

日文版只留原文并去掉淡化样式，中文版只留译文并去掉日文注音，插图、目录、版权页两本都完整保留。

```console
$ cargo run
源 EPUB: .\jp-zh.Ys.カイブツ×カノジョ (講談社ラノベ文庫).epub

读入 65 个条目

=== [ja] .\jp-zh.Ys.カイブツ×カノジョ (講談社ラノベ文庫).ja.epub ===
  保留 日文段  3215 / 中文段     0 / 中立段  156 / 丢弃  3215
  产物 65 个条目，首条目 mimetype(Stored) ✓ 符合规范
  正文 3215 段（另有图片/空行 156 段）；残留淡化样式 0 处；混入日文 0 段

=== [zh] .\jp-zh.Ys.カイブツ×カノジョ (講談社ラノベ文庫).zh.epub ===
  保留 日文段     0 / 中文段  3215 / 中立段  156 / 丢弃  3215
  产物 65 个条目，首条目 mimetype(Stored) ✓ 符合规范
  正文 3215 段（另有图片/空行 156 段）；残留淡化样式 0 处；混入日文 0 段

完成。
```

---

## 它解决什么问题

双语对照 EPUB 里两种语言是**逐段交替**的，读起来视线要来回跳：

```html
<p style="opacity:0.4;">　空から、何かが落ちてきた。</p>
<p>　有什么东西从天上掉了下来。</p>
<p style="opacity:0.4;">　僕はいつもの帰り道の風景で、『それ』を目撃してしまった。</p>
<p>　我在回家路上的风景中，目击了『那个』。</p>
```

想只读其中一种语言，就只能一段段手删。本项目自动完成这件事，且不依赖任何在线翻译或语言识别服务。

## 原理：不是"识别语言"，而是"读样式"

关键在于——这套源文件里两种语言**不是靠内容区分的，而是靠内联样式**：

| | 源文件里的写法 | 数量 | 含义 |
|---|---|---|---|
| 日文原文 | `<p style="opacity:0.4;">…</p>` | 3215 段 | 淡化显示；在文档顺序里先出现 |
| 中文译文 | `<p>…</p>` | 3371 段 | 正常显示；紧随对应日文段之后 |
| 语言无关 | `<p><br /></p>`、`<p><img …/></p>` | 156 段 | 空行 141 + 图片页 15，两本书都要 |

所以判别式只有一条：**`<p>` 的开标签带不带 `opacity` 样式**。之所以敢只靠它，是因为这套源文件满足四个可验证的条件：

- 39 个 XHTML（37 个含段落）里**只有这两种** `<p>` 形式，没有第三种变体；
- 3215 对日/中段落**严格交替**，没有出现连续两段同语言（0 例外）；
- 中文段落里**假名出现 0 次**；
- 414 个 `<ruby>` 注音**100% 落在日文段落内**。

也就是说切分零歧义，不需要语言识别模型。顺带的好处是：中文版会自动不含任何日文注音，无需单独剥 `<rt>`。

判别式被写死成 `opacity:0.4;` 这一个字面量，见下文[已知限制](#已知限制)。

## 快速开始

```bash
cargo run                    # 自动使用当前目录下的 .epub
cargo run -- <path.epub>     # 指定源 EPUB
cargo test                   # 47 个测试
```

需要支持 edition 2024 的 Rust（1.85+）。开发与验证环境为 1.95.0；最低版本未逐版本验证，实际下限还可能受 `zip` 依赖约束。唯一的直接依赖是 [`zip`](https://crates.io/crates/zip)。

## 输出

在源文件旁边生成两个文件：

| | 日文版 `*.ja.epub` | 中文版 `*.zh.epub` |
|---|---|---|
| `dc:title` | カイブツ×カノジョ (講談社ラノベ文庫) | 凯物×女友 |
| `dc:language` | `ja` | `zh-CN` |
| `dc:identifier` | `<原 id>-ja` | `<原 id>-zh` |
| 章标题 | プロローグ / 一章 / エピローグ | 序章 / 第一章 / 终章 |
| 导航标签 | 目次 / 奥付 | 目录 / 版权页 |
| `<ruby>` 注音 | 保留 | 无 |
| 插图 | 17 张 | 17 张 |
| 段落 | 3215 正文 + 156 中立 | 3215 正文 + 156 中立 |

中文名「凯物×女友」取自源书版权页（奥付），不是臆造的。注意 `dc:creator` **未改写**，两本书都保留源书的日文作者名。

## 实现里必须处理的四个坑

这些都是打开源文件后实际发现的，不是泛泛而谈：

1. **必须同时删掉淡化样式。** `opacity:0.4` 在对照排版里的语义是"这是原文"。日文版如果只删中文段却留着样式，整本书会是**淡灰色**的。`split.rs` 在保留日文段时把开标签重写为 `<p>`。
2. **5 个 CSS 文件全是 0 字节。** 样式全部内联，所以不能靠改 CSS 来切换语言——只能在 XHTML 层面改。
3. **源书元数据有错。** `dc:language` 写死成 `zh-CN`（对日文版是错的），`primary-writing-mode` 写 `horizontal-lr` 却又在正文用 `vrtl` 竖排。两者都已按实际内容改正。
4. **两本书的 `dc:identifier` 必须不同**，否则阅读器书库会把它们当成同一本书互相覆盖。实现用 `<原 id>-<语言>` 派生。

另外，源书的 `mimetype` 条目是 **Deflated（压缩）** 的，不符合 EPUB 规范；产物统一修正为**第一个条目 + Stored（不压缩）**。

## 安全网：宁可报错，不出半成品

拆错一本双语书最坏的结果是"静默产出一本混着另一种语言的书"，所以项目内置了三道检查，`main` 在自检不过时**以非零退出码结束**：

- **段落守恒**：源书每个段落都必须有归宿——进这本书、被另一本收走、或作为中立段两边都要。两本书各自满足 `留下的 + 丢弃的 = 6586`，不可能凭空消失或重复计入。
- **残留样式检查**：产物里 `opacity:0.4` 必须为 0 处。
- **串味检查**：中文版里含假名的正文段必须为 0 段。

实测把某一章的 `opacity` 标记全部抹掉（模拟"换了一本不符合约定的书"）：

```console
=== [ja] broken.ja.epub ===
  ⚠ 该语言下没有正文的页面: OEBPS/Text/part0008.xhtml
=== [zh] broken.zh.epub ===
  正文 3249 段（另有图片/空行 156 段）；残留淡化样式 0 处；混入日文 34 段
Error: "[zh] 产物未通过自检"      # 退出码 1
```

34 段日文混进了中文版，工具明确报错退出——而不是把它当作正常产物交付。

## 项目结构

```
src/
├── lib.rs        库根：模块声明 + 源书约定文档
├── main.rs       CLI 入口：参数、编排、打印（仅 84 行）
├── lang.rs       语言领域模型（ja / zh-CN / 书名）
├── paths.rs      决定读哪个文件、产物叫什么
├── epub.rs       ZIP 容器层：整包读入 / 写出
├── markup.rs     XHTML 片段层：切出 <p>，不含语言概念
├── split.rs      核心：按样式决定段落去留
├── metadata.rs   OPF / NCX / 章标题改写
├── pipeline.rs   编排：组装出一本书
└── audit.rs      产物回读自检
tests/
└── round_trip.rs 端到端集成测试
```

依赖方向是单向的，没有环：

```
markup ─┬─> split ────┐
        └─> metadata ─┴─> pipeline ─> main
lang ────┴──────────────────┘         ^
paths ────────────────────────────────┤
epub ─────────────────────────────────┤
audit ────────────────────────────────┘
```

两条设计约定：

- **`markup` 刻意不认识"语言"**，只认识标记结构；"带样式的是日文"这条业务规则属于 `split`。
- **所有模块返回数据、不打印**，格式化集中在 `main`。所以 `audit` 返回 `Report` 而不是直接输出，测试才能断言它。

`epub` 的读写是泛型（`Read + Seek` / `Write + Seek`），因此 `epub` 与 `audit` 的测试**全程在内存 `Cursor` 里跑**，不落任何临时文件。

## 作为库使用

各模块都是公开的，可以嵌入自己的流程：

```rust
use novelia_epub_bilingual_splitter::{audit, epub, lang::Lang, pipeline};

let entries = epub::read_path("book.epub".as_ref())?;

for lang in Lang::ALL {
    let (archive, stats) = pipeline::build(&entries, lang);
    println!("[{}] 留下 {} 段，丢弃 {} 段", lang.tag(),
             stats.paragraphs.paragraphs(), stats.paragraphs.dropped);

    let mut buf = std::io::Cursor::new(Vec::new());
    epub::write(&mut buf, &archive)?;
    buf.set_position(0);

    let report = audit::inspect(buf, lang)?;
    assert!(report.is_clean());
}
```

## 测试

47 个测试（44 个单元 + 2 个集成 + 1 个文档测试），`cargo clippy --all-targets` 无警告。

| 层 | 覆盖内容 |
|---|---|
| `markup` (8) | 段落切分、`<pre>` 不误判、未闭合尾部保留、容器不丢、中立段识别 |
| `metadata` (8) | OPF/NCX 改写、"一章"不会变成"第一第一章"、全角数字标题不动 |
| `split` (8) | 两语言各自的保留/丢弃、段落守恒、图片页不算空页、统计累加 |
| `pipeline` (5) | 条目数与顺序不变、二进制条目原样透传、缺 OPF 也不崩 |
| `epub` / `audit` / `lang` / `paths` (15) | 内存归档往返、mimetype 规范、串味与残留样式检出、路径规则 |
| `tests/round_trip.rs` (2) | 端到端：真实源书 + 手工构造的迷你双语书 |
| 文档测试 (1) | 编译校验上面的[库用法示例](#作为库使用) |

端到端测试把源书实测数字写成常量（6586 / 3215 / 156），一旦切分逻辑回归会立刻失败。

## 已知限制

- **判别式写死 `opacity:0.4;`**。换一本用别的方式标记原文的书（别的透明度、别的 class、`display:none` 等），需要改 `markup::FADING_STYLE`。好消息是不会静默出错：约定被破坏时会触发[安全网](#安全网宁可报错不出半成品)并以非零码退出。
- **中文版章标题靠手工映射表**，只覆盖本书出现的 10 个标题。源书的章标题**只有日文、没有中文对照**，任何自动化都无法凭空得到译名。
- **中文版沿用竖排**（`class="vrtl"`）以还原原书版式。若希望横排，需要自行在 `metadata::rewrite_raw` 里加一处 `vrtl` → `hltr` 的替换。
- **`dc:creator` 未改写**，两本书都保留源书的日文作者名 `浅倉イネ`。源书版权页里其实有中文译名「浅仓伊奈」，需要的话可以在 `metadata::rewrite_opf` 中一并改写。
- **输出不是字节级可复现的**：ZIP 写入器给每个条目打上当前时间戳，所以每次运行的 SHA256 都不同。不影响阅读，但如果你想用哈希做产物校验，需要给写入器设一个固定时间戳。
- **未处理加密/DRM 与 EPUB 3 的 nav 文档**。本项目针对的是 EPUB 2.0（`version="2.0"` + NCX）且无 DRM 的文件；遇到 `META-INF/encryption.xml` 不会解密。
- 源书体积按整体读入内存处理（本例 2 MB）。拆几百 MB 的书需要改成流式。

## 开发环境提示

本机沙箱下 `cargo add` / `cargo build` 首次拉取依赖会失败：

```
schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS
```

这不是网络不通（DNS 正常，Node 自带的 OpenSSL 能访问 crates.io），而是沙箱令牌拿不到 Windows 加密凭据，导致 cargo 的 TLS 握手失败。**依赖已全部缓存到 `~/.cargo`，日常 `build` / `test` / `run` 不受影响**；只有新增依赖时才需要放行网络访问。
